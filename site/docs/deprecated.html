Deprecated syntax and APIs

This page is the migration index for Lynxer's deprecated language syntax. Deprecated forms remain accepted where stated, but new code should use the replacement. Deprecation warnings are emitted for the declaration keywords, deprecated operators, tuple bracket coercions, and legacy methods where the parser/runtime supports them. suppressDeprecationWarning() suppresses runtime deprecation warnings; it does not make old syntax canonical.

Function declarations

Use fn for top-level functions, nested functions, and methods.

Deprecated declarationReplacementNotes
global name(...) { ... }fn name(...) { ... }Use a bare call in the same module.
func name(...) { ... }fn name(...) { ... }Use a bare call in the same module.
local name(...) { ... }fn name(...) { ... }Declare nested functions with fn; call them by name or qualified path.
local method(...) { ... } in a template or legacy classfn method(...) { ... }Method behavior is unchanged.
global.name(...) for a same-module functionname(...)Do not remove global. when it refers to a builtin or an imported namespace.
local.name(...) for a nested functionname(...) or parent.name(...)Use the nested hierarchy when calling from outside the declaring scope.

Legacy function declaration keywords produce a deprecation warning recommending fn. Call same-module functions by name, imported functions through <module>.<name>(...), and nested functions through their hierarchy. The former global. and local. function prefixes are unnecessary. The global. prefix still has builtin/namespace behavior in some contexts; do not mechanically remove it from builtin calls or native-module forwarders without checking what the name refers to.

Legacy class form

The class object form is deprecated in favor of template. Use template header parameters, build Type(args) named value;, and extending inheritance. The legacy form remains supported for compatibility; see classes for its init, new, extends, and super behavior.

Operator spellings

Use keyword operators instead of these deprecated symbolic spellings:

DeprecatedReplacement
==is
!=, not isisnt
&&and
||or
!!not
!&&nand
!||nor
&bitand
|bitor
^bitxor
~bitnot
!&bitnand
!|bitnor
!^bitxnor
<<bitleft
>>bitright

The symbolic forms still parse and run while warning at each use. A bare ! is not deprecated syntax; it is invalid.

Tuple assignment

Assign tuples using parenthesized tuple syntax rather than coercing a bracket list:

tuple current = (int 1, int 2);
current = (int 3, int 4);

Assigning a bracket list to a tuple variable is accepted for compatibility, but emits a deprecation warning. tupleCreate(...) and listToTuple(...) are the explicit conversion helpers. See tuples.

Other legacy syntax

The old exec({name}) codeblock invocation is replaced by exec(){{name}}; use the latter form. See codeblocks.
