Windows API standard libraries

On Windows, Lynxer exposes Win32 calls through the native-backed winAPI-amd64 and winAPI-arm64 standard-library modules. Import the module matching the process architecture with importAs:

fn setup() {
    importAs("winAPI-amd64", "windowsApi");
}

fn main() {
    println(windowsApi.getProcessId());
    println(windowsApi.getComputerName());
    println(windowsApi.getCurrentDirectory());
}

Most calls are kernel32; getKnownFolderPath uses shell32/ole32 for the Known Folder GUIDs. Both libraries ship with Windows, so nothing extra has to be installed.

On Windows arm64, import winAPI-arm64 instead. The module checks the host operating system and architecture for each operation. The API catalog below uses the windowsApi alias for either module.

Host availability

  • Calls require a Windows runtime and validate that the imported module matches the running process; there is no cross-architecture dispatch.
  • The legacy winAPI.* built-ins remain available but are deprecated. New programs should import winAPI-amd64 or winAPI-arm64.
  • A misspelled operation in the legacy surface reports the closest match, e.g. unknown winAPI function 'getProcesId'. You meant: getProcessId?.

Conventions

  • Failed Windows operations use the native API's scalar sentinels: -1 for a handle, size, position, byte count or free-space figure; false for a predicate; "" for a failed read. windowsApi.getLastError() returns the Win32 error code for the most recent call.
  • The original calls keep returning integer handles for compatibility. The *Handle helpers return first-class HANDLE/HWND objects, which can be passed directly to handle-taking calls. Close HANDLE objects with windowsApi.closeHandle(); socket objects must use windowsApi.closeSocket().
  • SOCKET and HANDLE are distinct template-backed object types. HWND is also distinct from kernel handles. To avoid named-type collisions when a program imports both architecture modules, concrete type names include the architecture suffix (HANDLE_amd64, HANDLE_arm64, and likewise for HWND and SOCKET). asHANDLE, asHWND and asSOCKET convert a raw integer result; they return none for the -1 failure sentinel.
  • These wrappers do not track ownership. Handles returned by moduleHandle/standardHandle and windows returned by consoleWindowHandle are borrowed; do not close them with closeHandle.
  • Typed producers are createFileHandle, currentProcessHandle, moduleHandle, createNamedPipeHandle, openNamedPipeHandle, openProcessHandle, createProcessHandle and standardHandle for HANDLE, consoleWindowHandle for HWND, and connectSocket, listenSocket and acceptSocket for SOCKET. handleValue, windowValue and socketValue convert an object back to its raw integer representation when needed.
  • Wrong argument types are source-located errors, e.g. windowsApi.readFile() failed: expects an integer handle and length.
  • Text is UTF-8 at the Lynxer boundary; the *W calls are used internally.

mode is "read" (OPEN_EXISTING), "write" (CREATE_ALWAYS, truncated), "append" (OPEN_ALWAYS, seek to end) or "readwrite" (OPEN_ALWAYS). seekFile positions absolutely from the start of the file.

fn main(){
    str path = windowsApi.getTempPath() + "demo.txt";

    int file = windowsApi.createFile(path, "write");
    if (file < 0) {
        println("cannot create: " + windowsApi.getLastError());
        return;
    }
    windowsApi.writeFile(file, "hello");
    windowsApi.closeHandle(file);

    int reader = windowsApi.createFile(path, "read");
    println(windowsApi.fileSize(reader));
    println(windowsApi.readFile(reader, 64));
    windowsApi.closeHandle(reader);
    windowsApi.deleteFile(path);
}

Use createFileHandle to opt into object handles without changing existing integer-returning calls:

fn main() {
    str path = windowsApi.getTempPath() + "demo.txt";
    any file = windowsApi.createFileHandle(path, "write");
    windowsApi.writeFile(file, "hello");
    windowsApi.closeHandle(file);
    windowsApi.deleteFile(path);
}

Shell, clipboard and dialogs

FunctionReturns
windowsApi.shellOpen(path)whether ShellExecuteW accepted the request
windowsApi.shellOpenWith(path, arguments, verb)the same, with an explicit verb such as "edit"
windowsApi.messageBox(text, title)the MessageBoxW result
windowsApi.clipboardGet()the clipboard's Unicode text, or ""
windowsApi.clipboardSet(text)whether the clipboard was updated
windowsApi.notify(title, message)whether a tray balloon was queued

shellOpen/shellOpenWith are fire-and-forget: they return as soon as the shell accepts the request. messageBox blocks until the user dismisses the dialog, so it is unsuitable for unattended programs. notify queues a tray balloon for five seconds and returns immediately; it needs an interactive console window. Clipboard and notification access need a window-station/desktop that permits it; under a service or a headless session they return the failure sentinel instead of raising.

Named pipes

FunctionReturns
windowsApi.createNamedPipe(name)a server handle, or -1
windowsApi.connectNamedPipe(handle)whether a client connected
windowsApi.openNamedPipe(name)a client handle, or -1 after a 5 s wait
windowsApi.readNamedPipe(handle, length)up to length bytes, or ""

windowsApi.peekNamedPipe(handle)bytes available, or -1

Names are relative to \\.\pipe\; a full \\.\pipe\name path is also accepted. openNamedPipe retries while the server is still creating the pipe, so a client may start before the server. Pipe handles are ordinary handles and are released with windowsApi.closeHandle. Reads and writes are blocking.

fn main(){
    int server = windowsApi.createNamedPipe("lynxer-demo");
    // In another process:
    //   int client = windowsApi.openNamedPipe("lynxer-demo");
    windowsApi.connectNamedPipe(server);
    println(windowsApi.readNamedPipe(server, 64));
    windowsApi.writeNamedPipe(server, "pong");
    windowsApi.disconnectNamedPipe(server);
    windowsApi.closeHandle(server);
}

TCP sockets

FunctionReturns
windowsApi.tcpConnect(host, port)a connected socket, or -1
windowsApi.tcpListen(host, port)a listening socket, or -1
windowsApi.tcpAccept(socket)a connected socket, or -1
windowsApi.socketLocalPort(socket)the bound local port, or -1
windowsApi.socketSend(socket, text)bytes sent, or -1
windowsApi.socketReceive(socket, maxBytes)received bytes, or "" on failure/closed connection
windowsApi.socketShutdown(socket, direction)whether shutdown succeeded
windowsApi.closeSocket(socket)whether it closed
windowsApi.getSocketError()the last Winsock error code

tcpConnect and tcpListen accept a host string and a port from 0 to 65535; an empty listen host binds to all local interfaces. Port 0 asks Windows to choose a port, which can then be read with socketLocalPort. tcpAccept and socketReceive block until a connection or data arrives. socketReceive reads at most 16 MiB per call, and returns at most the bytes currently available; TCP does not preserve message boundaries. socketSend may send fewer bytes than requested, so callers should retry the unsent suffix when sending larger payloads. Its argument is UTF-8 text, not an arbitrary binary buffer.

Socket values are integer SOCKETs, not Win32 HANDLEs; release them with closeSocket, not closeHandle. connectSocket, listenSocket and acceptSocket return first-class SOCKET objects (or none on failure); the raw tcpConnect, tcpListen and tcpAccept functions remain available. socketShutdown(socket, "send"), "receive" or "both" to shut down one or both directions. Failed native operations return their sentinel; call getSocketError() immediately to retrieve the Winsock error before making another socket operation.

fn main() {
    int listener = windowsApi.tcpListen("127.0.0.1", 0);
    int port = windowsApi.socketLocalPort(listener);
    int client = windowsApi.tcpConnect("127.0.0.1", port);
    int accepted = windowsApi.tcpAccept(listener);
    windowsApi.socketSend(client, "hello");
    println(windowsApi.socketReceive(accepted, 64));
    windowsApi.closeSocket(client);
    windowsApi.closeSocket(accepted);
    windowsApi.closeSocket(listener);
}

The long tail

Anything not in the tables above — other DLLs, the *A/*W pairs, structs and APIs not wrapped here — is reachable through the FFI built-ins (native-modules). On Windows x64, cdecl: uses the platform's unified calling convention. On 32-bit Windows, use stdcall: for Win32 APIs declared WINAPI/__stdcall; for example:

fn main(){
    int user32 = ffiLoadLibrary("user32.dll");
    functionAddress box = ffiLookup(user32, "MessageBoxA");
    ffiCall(box, "stdcall:int32(uintptr,cstring,cstring,uint32)",
            [int 0, str "hello", str "lynxer", int 0]);
    ffiCloseLibrary(user32);
}

The wrappers currently cover the documented kernel32, Winsock and selected shell APIs; other DLL calls can use the FFI directly.
