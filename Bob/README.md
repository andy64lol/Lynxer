# Bob

`Bob` is the package manager for the **Lynxer** language, named after the bobcat —
a species of lynx. It is a standalone Rust component inside the Lynxer repository,
**kept separate from the interpreter**: it lives in `Bob/`, has its own Makefile
and version, and only knows which Lynxer version it supports.

Bob:

- **scaffolds** a project or a reusable module (`bob --init`, `bob --init-module`);
- **publishes** a module to a GitHub Release (`bob publish`);
- **installs** a module through the registry (`bob install`);
- **installs itself** onto your `PATH` (`bob --install-exec`).

## How Lynxer finds modules

A Lynxer module is a **directory with a manifest that names its entry point** —
`modules/<name>/`, like Node's `node_modules/<name>/`. A bare `import("<name>")`
walks up from the importing file, finds the nearest `modules/<name>/`, and loads
the file named by `entry` in `modules/<name>/module.toml` (falling back to
`index.lynx`, then `main.lynx`). See [../docs/modules.md](../docs/modules.md).

```text
<project>/
  modules/foo/
    module.toml        # [module] name="foo" version="0.1.0" entry="src/main.lynx"
    src/main.lynx      # global foo() -> str { return "foo bar!"; }
  main.lynx            # global setup(){ import("foo"); }
```

`bob --init-module` writes that same `module.toml` and `src/main.lynx`, and
`bob publish` packs them. The manifest's `entry` is exactly what the interpreter
reads once the module is installed under `modules/<name>/`.

## Commands

| Command | Effect |
| --- | --- |
| `bob --ver` | Prints the Bob version and the Lynxer version it supports. |
| `bob --init` | Creates `bob/bob.toml`, `bob/bob-lock.toml` and an empty `bob/packages/`. |
| `bob --init-module` | Creates `module.toml` and `src/main.lynx` in a reusable module project. |
| `bob --install-exec` | Installs the `bob` executable under the prefix (`BOB_PREFIX`; `/usr` on Unix, a per-user directory on Windows). |
| `bob --uninstall-exec` | Removes the executable `--install-exec` wrote. |
| `bob publish` | Validates the current module, packages it as a ZIP, and uploads it as a GitHub release asset. |
| `bob install <name> <version>` | Resolves a package and downloads its release asset. |
| `bob registry add\|list\|config` | Manage local package→repository mappings in `~/.bob/registry.json`. |
| `bob config set\|get\|show\|unset\|path` | Manage `~/.bob/config.json` (the REST registry link and GitHub token). |
| `bob --help` | Usage. |

```console
$ bob --ver
bob 0.1.1
supported lynxer 0.1.8.3

$ bob --init
Created bob/bob.toml
Created bob/bob-lock.toml
Created bob/packages/

$ bob --init-module
Created module.toml
Created src/main.lynx

$ bob --install-exec
Installed /usr/bin/bob
```

## Project layout

A Bob **application** keeps its manifest and lock file under one `bob/` directory:

```text
bob/bob.toml        the manifest ([package], [dependencies])
bob/bob-lock.toml   the lock file, generated by Bob
bob/packages/       downloaded package archives
```

Both files use the same TOML model Cargo uses, so they read the way a Rust
developer expects.

## Module projects

`bob --init-module` scaffolds a reusable module instead of an application:

```text
module.toml      the module manifest ([module], [dependencies])
src/main.lynx    the module source
```

`module.toml` carries the `[module]` metadata the registry and the interpreter
both use — `name`, a semantic `version`, and an `entry` that must be a safe
`.lynx` path under `src/`:

```toml
[module]
name = "foo"
version = "0.1.0"
edition = "2026"
entry = "src/main.lynx"

[dependencies]
```

`src/main.lynx` follows the pure-module shape in
[../docs/extending.md](../docs/extending.md): a `////` documentation header, an
empty `global setup()`, and exported `global` functions. Modules are imported by
name, not run, so there is no `main()`:

```lynx
global add(int left, int right) -> int { return left + right; }
```

## Configuration

Bob reads two settings from `~/.bob/config.json`:

| Key | Meaning |
| --- | --- |
| `rest-api` | Base URL of the Bob REST registry (for example `https://lynxer.netlify.app`). Resolves a package name to its GitHub repository via `POST /api/resolve`. |
| `github-token` | GitHub API token used to create releases (`publish`) and download assets (`install`). |

```console
$ bob config set rest-api https://lynxer.netlify.app
Set rest-api in /home/you/.bob/config.json
$ bob config set github-token ghp_...
Set github-token in /home/you/.bob/config.json
$ bob config show
rest-api = https://lynxer.netlify.app
github-token = ghp_****
config file: /home/you/.bob/config.json
```

`bob config get <key>` prints one value (the token is masked), `unset <key>`
removes one, and `path` prints the file location. On Unix the file is written
with `0600` permissions because it can hold a token.

Each setting can be overridden by an environment variable, which takes precedence
over the file: `BOB_REST_API` for the registry, `GITHUB_TOKEN` for the token.
`BOB_CONFIG_DIR` overrides the directory holding `config.json` (default `~/.bob`).

## The registry

The registry maps a package **name** to its GitHub repository and version. It is a
**Supabase** database (`public.modules`, one row per module) with two front ends:

- the **API** — `POST /api/resolve` on Netlify (`lynxer-registry/`) — which `bob`
  calls;
- the **Bob Index** — a PyPI-like page on Render (`BobI/`) for people.

`POST /api/resolve` takes `{"name": "..."}` and answers
`{"owner": "...", "repository": "...", "version": "..."}` (or `404` when the name
is unknown). The public API is at <https://lynxer.netlify.app>; see
[docs/bob-registry.md](../docs/bob-registry.md) and
[docs/bob-index.md](../docs/bob-index.md).

A name resolves in this order: the **REST registry** (when `rest-api` is set),
then the local `~/.bob/registry.json` mappings (`bob registry add`), then a small
set of built-in defaults.

## Publish and install

`bob publish` reads `module.toml`, packages it as `manifest.toml` alongside the
files under `src/`, creates a GitHub release tagged with the module version, and
uploads the archive as `{name}-{version}.zip`:

```text
my-module-1.0.0.zip
├── manifest.toml              # the current module.toml
└── src/
    └── main.lynx
```

Before uploading, Bob validates the archive: the name matches, the version is
canonical semver, every source path stays under `src/` (no traversal, no symbolic
links), and the size and file count stay within limits.

`bob install <name> <version>` resolves the package to a GitHub repository,
downloads the matching release asset into `bob/packages/{name}-{version}/`, and
reports its SHA-256.

Both commands need a GitHub token (from `github-token` or `GITHUB_TOKEN`). Tokens
are sent only to GitHub over HTTPS, never to the registry — and never put one in
`module.toml`.

> **Status.** `bob install` writes the downloaded archive as
> `bob/packages/{name}-{version}/archive.zip`; it does not yet extract it into
> `modules/<name>/`, so an installed module is not importable until that lands.
> Tracked in [todo.md](todo.md).

## Worked example

Publishing and installing the `foo` module end to end:

```console
# 1. scaffold and edit the module
$ bob --init-module
$ cat src/main.lynx          # global foo() -> str { return "foo bar!"; }

# 2. publish it as a GitHub release
$ GITHUB_TOKEN=... bob publish
Published foo@0.1.0(sha256:fTCAq0Eq...=)   # → release 0.1.0, asset foo-0.1.0.zip

# 3. register the name → repository mapping (see lynxer-registry/registry.json)
#    "foo": { "repository": "andy64lol/foo", "version": "0.1.0" }

# 4. install it into a project
$ bob install foo 0.1.0
Installed foo@0.1.0(sha256:fTCAq0Eq...=)
```

A program then uses the module through the interpreter's directory-module
resolution:

```lynx
// main.lynx  (with the module present at modules/foo/)
global setup(){ import("foo"); }
global main(){ println(global.foo.foo()); }   // foo bar!
```

## Build

```bash
make -C Bob                          # or, from the repo root: make buildBob
Bob/target/release/bob --ver
```

## Platforms

Bob is Rust and builds for **Linux and Windows**, on AMD64 and ARM64, each covered
by its own CI job; nothing in the CLI is OS-specific, so it is portable to other
platforms too. The project-relative paths printed by `bob --init` always use `/`,
so a scaffold reads the same everywhere.

On Windows, run the Makefile from an MSYS2 or Git Bash shell (it needs the POSIX
tools). `cargo build --release` works from any shell, because the Makefile is only
a wrapper.

The Windows build uses a **static CRT** (`-C target-feature=+crt-static`), so
`bob.exe` is standalone and runs from `cmd.exe` or PowerShell, not only MSYS2. The
Windows job verifies that directly: it runs the freshly built `bob.exe` natively
(no MSYS2 on `PATH`) and checks it writes `bob\bob.toml`.

Bob has its own CI, separate from the Lynxer jobs. Four workflows
(`build-bob-linux-amd64.yml`, `build-bob-linux-arm64.yml`,
`build-bob-windows-amd64.yml`, `build-bob-windows-arm64.yml`) build it and run the
self-check. Like the rest of CI, they run on every push and pull request to `main`.
